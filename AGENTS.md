# Mill engineering guidance

Read README.md and docs/b1-release-brief.md before implementation. The user has requested a complete, usable v1 release, not a skeleton or a smaller substitute for the agreed release scope.

## Product and architecture

- Build a focused task list for teams and external clients. The current v1 scope uses alphabetical boards and six fixed task statuses; Kanban, custom statuses, manual ordering, labels, task parents/subtasks, checklists, portable export/import, and email task notifications are excluded. Existing task and subtask records must survive as independent tasks; unrecognized old status names become Todo. Agents are removed completely: no Agent identities, settings, assignment fields, filters, endpoints or MCP tools. Tasks may have a human assignee. Personal and team API keys require Name, Permissions and Expires after selections; their explicit grants apply to REST and MCP. Personal grants remain bounded by the owner's active membership and role, while team grants use team policy independently of the creator's later membership. MCP OAuth authorizes a human-owned connection with read/write scopes and optional approved boards; it must revalidate the owner's active membership and current role. Activity records the responsible human or team key and connection type without an Agent identity. Hosted execution and orchestration are outside the product scope.
- Use the adjacent Towbar checkout as a read-only reference for current engineering conventions, OSS-safe UI primitives, authentication, API/MCP, Docker packaging, CI, documentation, and release verification. Do not edit Towbar or assume historical notes describe its current code.
- Keep Mill self-contained. A public install and contributor checkout must work without access to private Avgeek packages, paid component libraries, licensed fonts or icons, or local sibling checkouts. Preserve attribution when adapting Apache-licensed code.
- Follow Node.js 24, pnpm, TypeScript, clear owning packages, shared contracts, PostgreSQL migrations, reproducible builds, and container health-check conventions where relevant. Add durable background jobs only where they are needed; do not copy Towbar's deployment infrastructure into a task board.
- Authentication, authorization, validation, and persistence belong on the server. Apply permissions consistently across UI, REST, and MCP. Do not rely on hidden UI controls for security.

## UI and language

- Show submission progress inside the initiating button and reserve its label width. Do not insert separate saving text or pending-only footers that shift the form or dialog layout.
- Reuse or adapt the existing OSS-safe Towbar design-system components and tokens. Do not create custom buttons, selects, dialogs, chips, or typography when a shared component covers the behavior.
- All success and error feedback uses the shared toast alerts across the app, including authentication, validation, loading failures, dialogs and clipboard actions. Shared ErrorMessage/FieldError emit toasts without inline content. Each failed attempt must notify again, while ordinary rerenders must not repeat the same notification. Keep drafts, pending controls and retry actions in the initiating page/dialog; do not reserve space for empty feedback containers. Native form validation uses toast feedback and focuses the first invalid field. Keep toast dismissal reachable without hover, including above modals. Before React can load, startup recovery uses a dismissible native fallback toast with self-contained styling. Error pages keep their title and navigation controls, with failure explanations in toasts. Resource statuses and contextual security guidance remain factual UI.
- Resource lists use the shared Towbar-adapted `ResourceTable` recipe where applicable, with explicit row headers and stacked mobile details. Sessions uses Session, Session ID, Last active, Expires, Status and Actions columns; Current uses the theme accent, Active uses success. Revoke requires confirmation and retains pending/retry recovery in that dialog. Verify server absence after a failed revocation response before resolving it as complete. Initial query loading uses the shared invisible status announcement, without a false empty state.
- Use the actual Towbar People composition: page actions above the tables, no redundant Members/Invitations headings or introductory paragraphs. Use shared `TableCellStack` and `TableCellDescription`: primary `text-sm/5 font-normal`, secondary `text-xs/4 font-normal text-muted`, and the shared line gap. Use semantic role/status Chips and the shared `Avatar({email,name})` with normalized-email SHA-256 Gravatar lookup and initials fallback.
- Buttons use the shared primary, secondary, or danger variant. The header breadcrumb navigation toggle and task-page Back to board use inline/ghost styling; the task edit action is primary and opens a title/description modal. Body copy, form introductions, general instructions, status messages, empty-state messages and confirmations use `text-sm`, whether inside or outside a form. Only field descriptions and form footnotes use `text-xs` for explanatory copy; do not use FieldDescription for a form's introductory paragraph. Keep intentional compact labels, timestamps and table secondary text at their established sizes. Widget titles and icons follow the shared Towbar sizes. Last-administrator guidance belongs in the disabled delete action's keyboard/touch-accessible Tooltip; retain the server protection.
- Keep user-facing text simple. Avoid internal identifiers, attempt details, implementation jargon, placeholder copy, empty features, and disabled future-feature navigation.
- Operate → Boards opens `/boards`, an alphabetical card overview with server-counted Backlog, To Do and In Progress tasks, with colored status icons before the numbers below each label and no icon beside the board name. Individual board tables keep Search tasks above the table and use the secondary sidebar for filters and sort; mobile opens filters through the navigation drawer. Board titles truncate as needed so New task and the actions menu remain on the heading row at the right. Do not return to the old board directory sidebar or automatic last-board navigation. Preserve overview retry and complete directory loading.
- Page-heading icons use the shared 24px size; board overview count icons use 20px beside their 18px values. Status options, chips, table rows and navigation retain 16px icons, and compact buttons retain their native sizing. Keep the icon library's default stroke width and scope heading sizing to the leading icon wrapper.
- Tasks open on dedicated pages. UI creation asks for Title, Type, Description and Assignee; REST/MCP creation retains its full field contract. Task fields save independently, with local retry and conflict controls that preserve drafts, and error feedback in toasts. Preserve board search, all filters, sort, page and page size in URL parameters and task return links.
- Tasks have Task or Bug types, defaulting to Task for new and existing records. Show Type during creation and before Status on the task page. Use Task01Icon in the theme accent for Task and Bug02Icon in red for Bug, including before the task ID in desktop and mobile tables. Type saves independently with the existing retry/conflict behavior and is validated and persisted through REST/MCP.
- Duplicate task is a writable task-menu action that opens the shared creation modal. Prefix the title with `[Copy] `, preserve description/type/priority, start at Backlog and leave assignee/due date empty. Create only after confirmation, with a fresh identifier and no copied comments/history. Preserve the draft and idempotency key through failed confirmations.
- Task properties show optional Start date immediately before Due date. Both are nullable calendar dates that save independently and are validated/persisted through REST/MCP. Existing tasks start without a start date; duplication leaves both dates empty.
- Board tables show Task ID in its own column before Task at widths of 640px and above. On smaller mobile screens, keep the ID beneath the title. Both desktop ID and title links preserve the board view parameters. Task IDs remain fully visible without truncation; size the ID column to its content and let long titles truncate instead.
- Without an explicit status filter, hide Done and Won't Do tasks after 24 hours in their current status. Other edits must not reset that clock. Explicit status filters include older matching tasks; direct task links remain available. Apply this server-side to UI, REST/MCP, totals and pagination revisions.
- Keep the application page layout identical to current Towbar: broad `max-w-7xl`, 16px horizontal gutters (`px-4`) at every width, 80px bottom padding (`pb-20 sm:pb-20`) and 20px shared page heading padding. Task details use the shared content grid in normal document flow; scroll the whole page without fixed-height panes, independent task scroll areas or negative margins.
- Match Towbar's secondary filter composition: Sort tasks above Filter tasks, a visible Sort order label, compact muted labels with an 8px inset, 12px control gutters, 16px field spacing, and leading icons. Keep this label styling scoped to secondary sections; task and creation form labels retain their normal hierarchy.
- Desktop filter popovers use the board overlay host outside the sidebar's clipping ancestors. Mobile filter popovers stay inside the navigation drawer for focus containment. Keep both hosts within the authenticated access boundary.
- Select popovers cap at 20rem or the viewport width minus 32px, even with wider form triggers. Truncate long option names with ellipses while preserving complete accessible names.
- Match Towbar small-button sizing: 34px with touch input and 32px with fine input, using the shared `text-xs/4` and 14px icon defaults. The navigation toggle stays 32px. The Boards page uses a primary Create Board button at the right end of the page-heading row. Appearance and notification controls use the published defaults: 36px on desktop and 40px on phones. Do not enlarge all buttons through a mobile media query; retain the distinct input, checkbox and navigation-row sizing.
- The primary sidebar places personal and team settings under Settings. Do not add a separate People item or an empty Workspace group. Account Settings is available to every active member through the primary sidebar and grouped Account/Mill identity menu. Use the secondary sidebar for focused Profile, Preferences, Email & Password, Passkeys, Sessions, API Keys, MCP Connections and MCP Guide pages. Passkeys uses `/settings/passkeys`; keep `/settings/two-factor` as a compatibility route, passkeys are the only second factor. Team Settings uses `/team-settings/general`, `/team-settings/members`, and `/team-settings/team-api-keys`; retain `/settings/workspace` and `/settings/members` as redirect aliases. Team Settings remains administrator-only; member and team key management are reached there. Keep the owning primary item highlighted throughout each area. Keep OAuth connections on MCP Connections, separate from API keys. Personal API keys belong in Account Settings; team API keys belong in Team Settings. Keep `/settings/security` as the Email & Password compatibility route. Do not add unsupported email delivery or workspace audit settings.
- Authentication, account settings and team settings must use the published `@avgeek-oss/design-system` patterns and their standard headings, field labels, instructions, action labels and layout. Do not duplicate these compositions or override their fixed copy in Mill. Keep branding, backend adapters, access rules and truthful capability guidance in the app. If a supported security or invitation flow needs a new shared surface, extend the shared package before consuming it; keep invitation email verification, passkeys and passkey recovery distinct.
- Verify actual rendered desktop and mobile routes in both themes. Check keyboard, touch, wheel/trackpad scrolling, focus, popover height, long content, empty states, and errors.
- Preserve independent sidebar expansion across navigation; reserve icon dimensions and preserve logo aspect ratios. Select menus must scroll correctly inside modal overlays and their search fields must use the established padding.
- Mobile navigation retains the outgoing primary/secondary contents and drawer width until exit completes. Keep route-owned filter portals mounted through that exit; reopening during exit releases the destination navigation. Desktop navigation stays immediate, and reduced motion must not wait for a timer.
- Use compact descriptive text and consistent title/description hierarchy. Separator lists should have symmetric first/last spacing. Pending status and progress belong in the initiating dialog; success and error feedback belongs in toasts; use existing action components for recovery and dedicated 404/500 pages.
- Passkeys are the only second factor. Do not implement authenticator-app setup or TOTP verification. Keep passkey recovery distinct from invitation email verification and operator account recovery. Keep mobile charts compact, with enough plot headroom, if charts are genuinely useful.
- Respect reduced motion, meaningful accessible names, readable contrast, and touch-sized targets. Do not hide essential actions behind hover.

## Delivery and review

- The implementation task uses GPT-6 Sol with High reasoning. The user explicitly permits bounded subagent work where useful independent work can run in parallel. Assign clear file ownership, integrate every result, and perform independent final reviews.
- Maintain a requirements/evidence matrix for every v1 requirement. Do not claim a feature is complete from a green narrow unit test, mocked screenshot, README, intent, or scaffold.
- Add meaningful tests for permissions, persistence, concurrency, authentication, integration boundaries, installation, backup/restore, and core browser journeys. Avoid tests that only mirror implementation.
- Run pnpm verify (or the complete documented equivalent), real-database integration checks, production builds, and container smoke checks. Fix failures; do not weaken tests, skip gates, or label unresolved defects as acceptable release work.
- Preserve the applied `001_initial.sql` checksum and add forward migrations for API-key policy changes. Startup must reject incompatible retired migration ledgers without altering their data; pre-launch conversion requires a recoverable source snapshot and verified data preservation. Never rewrite an applied migration.
- Keep secrets out of code, artifacts, screenshots, and logs. Use disposable isolated local databases and containers for verification.
- Keep the GitHub repository private. Work on a development branch with reviewable commits and a PR when implementation is ready. Do not change repository visibility, merge your own release PR, deploy to production, buy a domain, or publish public artifacts without the coordinating task's final review and the user's applicable authorization.
- Report exact commits, CI runs, runnable preview URLs, rendered screenshots, and remaining gaps. A progress report is not a release-ready claim.
