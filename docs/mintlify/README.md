# Mintlify staging project

The maintained source guides live one directory up. From the repository root, run `node tools/build-mintlify-docs.mjs` to refresh this project. The generator adds page metadata, maps the source `api.md` to `/rest-reference` because Mintlify reserves `/api`, and rewrites links between the included guides. Edit the source guides, then regenerate; do not edit generated pages by hand.

Run `npx --yes mint@4.2.970 dev` from this directory for a local preview, `npx --yes mint@4.2.970 broken-links` to inspect site links, and `npx --yes mint@4.2.970 validate` to check the build. Mintlify must be configured to use this directory as its project root. The project, deployment branch, preview URL, GitHub App repository access, and custom domain still need verification in the owner's Mintlify account. Do not connect a private repository or publish these pages until the release candidate and access scope are approved.

The proposed public layout is `mill.fyi` for the product page and `docs.mill.fyi` for Mintlify. As observed on 2026-10-02, the apex already serves a Mintlify Starter Kit page, while `docs.mill.fyi` does not resolve. First identify the existing Mintlify project URL, connected repository and branch, and intended use of that starter. Confirm the layout with the owner before changing either project's domain or DNS. There is no hosted Mill app in this plan; operators install their own instance at a URL they choose. Once the approved project is ready, configure `docs.mill.fyi` in its Domain Setup and follow the DNS records it displays. Verify HTTPS, canonical URLs, redirects and page availability after DNS propagation and any authorized apex switch. Keep source links on the product site pointed at the repository only after its visibility and release artifacts are approved.
